# Markdown 预览阅读风格研究

研究日期：2026-10-12。目标文档是说明、笔记、表格与代码混合的通用中文 Markdown，首要权重是与 Codex 的融合程度。研究部分保留实施前的取证状态；后续确认与实现记录见文末。

建议优先试验「融入 Codex 的现代中性文档」：先统一背景、字体、文字颜色、边线和控件，再以清楚的标题层次、中文段落节奏和稳定的表格、代码表现形成品质感。技术文档与笔记路线可以作为密度调节的备选。这个选择是针对当前用途的设计判断；参考产品的知名度不能证明用户偏好。

## 一级资料能够证明什么

- GitHub 的 Primer 强调清楚、高效的阅读，建议用语义标题、字重和排版建立层次，避免把颜色作为主要强调手段；其正文通常左对齐。Primer 的 Markdown 样式作用于独立的 `markdown-body` 内容容器。[Primer 排版原则](https://primer.style/product/getting-started/foundations/typography/)、[Primer Markdown 内容说明](https://primer.style/product/getting-started/react/#markdown-content)
- VitePress 官方将默认主题定位为文档主题，允许分别调整 CSS 变量和站点布局。其正文 CSS 使用适度的标题尺寸、段落行高、细边线引用；表格和代码各自处理横向溢出。这些是可借鉴的正文做法，导航栏、站点品牌与首页封面属于另外的层次。[VitePress 默认主题](https://vitepress.dev/guide/extending-default-theme)、[正文 CSS 源码](https://github.com/vuejs/vitepress/blob/main/src/client/theme-default/styles/components/vp-doc.css)
- Typora 官方主题文档围绕 `h1`、`p`、`blockquote` 等内容元素编写 CSS，并提供字体、行距、段距、代码和写作区域宽度等独立定制项。官方没有规定唯一的最佳中文 Markdown 风格。[Typora 主题文档](https://theme.typora.io/doc/)、[样式定制说明](https://support.typora.io/Add-Custom-CSS/)
- W3C 中文排版需求草案认为行长应按字体、版式和媒介选择；书籍的 17–40 字行长仅为参考，并建议横排正文不宜超过 48 字。文中的「行距」指字框之间的空白；同字号时行高等于字号加行距。这是排版参考草案，不是 Markdown 的强制规范。[CLREQ 页面设计](https://www.w3.org/TR/clreq/#page_design)
- WCAG 2.2 的 AA 要求提供可量化的阅读底线：普通文字对比度至少 4.5:1，大字至少 3:1；普通横排内容在等效 320 CSS px 宽度应能重排，确实需要二维布局的表格等有例外。这些要求不能替代审美判断。[文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[内容重排](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

`github-markdown-css` 可以作为独立正文样式参考：该项目提供 `.markdown-body` 样式与系统明暗主题支持。它由 sindresorhus 维护，是 GitHub 样式的复刻项目，不能称为 GitHub 官方样式库。[项目说明](https://github.com/sindresorhus/github-markdown-css)

## 正文与站点外壳的边界

正文层负责标题、段落、列表、引用、表格、代码、图片和公式的阅读关系。站点外壳负责品牌、导航、侧栏和页面入口。对任意 Markdown 文件而言，文档未必有首页标题、作者、摘要或封面图，因此不能依赖这些结构营造外观。

针对当前预览用途，建议让正文直接进入阅读区。标题保持文档标题的身份；正文样式应同时适应没有 H1、多个同级标题、密集列表和代码开头的文件。整篇纸面卡片、大面积标题底色、装饰章节编号和大量圆角容器会占用分栏空间，并给普通段落添加原文没有表达的视觉结构。这是本项目的设计判断，不是官方资料禁止这些设计。

Codex 嵌入预览与独立浏览器预览可以采用不同的外壳：前者减少重复导航与边界，后者按需保留独立页面的标题、目录入口和外侧留白；两者共用正文排版。Codex 的文件路径、标签栏和原生面板外框属于宿主，插件不应尝试向它们注入样式。

## Codex 融合的能力与证据边界

MCP Apps 2026-01-26 规范定义了可选的 `hostContext.theme`、`hostContext.styles.variables` 和字体 CSS。变量包括背景、文字、边线、字体及圆角；宿主可以只提供其中一部分，或完全不提供 `styles`。规范还定义了 `ui/notifications/host-context-changed` 的局部更新通知。因此「协议支持宿主样式」不能推出「当前 Codex 已实际发送完整样式」。[MCP Apps 规范](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx#theming)

研究开始时的源码只证明下列状态：

- `host-bridge.js` 的 `initialize()` 使用 2026-01-26 协议，最后只返回 `result.hostCapabilities`，没有保留或传递初始化响应中的 `hostContext`；`connect()` 通过 `openai:set_globals` 获取文档输出，未读取主题或样式。源码中没有处理 `ui/notifications/host-context-changed`。[宿主桥接源码](../plugins/markdown-preview/assets/host-bridge.js)
- `reader.js` 使用 `matchMedia('(prefers-color-scheme: dark)')` 决定当前阅读主题。系统偏好不一定等于 Codex 应用内的主题选择。`viewer.html` 自行定义背景、文字、边线与强调色，并未使用上述宿主样式变量。这是研究开始时的实现事实，不证明 Codex 缺少相应能力。[阅读脚本](../plugins/markdown-preview/assets/reader.js)、[预览样式](../plugins/markdown-preview/assets/viewer.html)

后续接入建议是：确认实际初始化响应和更新通知；宿主样式存在时使用其语义变量，并提供缺失变量的中性回退；宿主主题存在时统一阅读区与图表主题，没有宿主主题时保留系统主题回退。官方 SDK 提供应用样式变量的辅助方法，但不要求为了样式而重写全部现有桥接。[官方样式辅助方法](https://apps.extensions.modelcontextprotocol.io/api/functions/app.applyHostStyleVariables.html)

视觉上建议减少预览外层的独立品牌感：阅读区采用单层表面，控件与宿主的密度和层次一致，目录、源码和浏览器入口作为并列的次级控件，强调色主要服务链接和有明确语义的提示。中文正文仍可拥有适合阅读的行高；融合不等于把正文压缩到工具栏字号。

本轮没有读取当前原生 Codex 窗口，也没有获得实际 `hostContext.styles` 数据，因此无法现场取色或宣称像素匹配。当前融合结论属于架构取证与设计建议，需在实际 Codex 分栏、主题切换和已安装插件中确认。ChatGPT Apps SDK 的样式支持不作为当前 Codex 支持的证明。

## 三条候选路线

以下名称是便于讨论的设计方向，不对应完整复制某个产品。

| 路线 | 正文性格 | 表格与代码 | 适用判断 |
| --- | --- | --- | --- |
| 融入 Codex 的现代中性文档，优先试验 | 优先继承宿主无衬线字体与语义配色，适中密度，靠字号、字重和留白建立层次 | 浅层次表头、清楚边界、克制代码底色 | 最适合说明、笔记、表格与代码混合的默认阅读 |
| 清晰技术文档 | 同一套中性字体，章节间隔更明确，列表略紧凑 | 强化表头、代码可读性和必要的语言标识 | 更适合 README、配置说明和操作手册；可作为密度备选 |
| 舒展知识笔记 | 同一套中性字体，段落和引用更舒展，分隔线更弱 | 保留完整能力，减轻表格网格的视觉重量 | 更适合连续文字和会议笔记；不借助衬线字体制造杂志感 |

三条路线共用宿主语义配色或同一套中性回退，不为展示差异额外加入品牌配色。字体、密度和信息层次应先决定，再决定是否需要少量强调色。

## 默认路线的具体试验原则

下列数值与取舍均为项目建议，尚未作为实现规格或用户认可的风格。

| 元素 | 建议起点 | 目的与边界 |
| --- | --- | --- |
| 正文 | 中文系统无衬线字体；16 px 起步，行高约 1.65–1.8 | 兼顾混排与长文；字体实际字面不同，仍需用真实中文样本确认 |
| 阅读宽度 | 宽窗约 34–42 个汉字的行宽，窄窗随可用空间收缩 | 控制扫读距离；这是试样范围，不照搬英文的 80 字符经验值 |
| 标题 | H1 约 28–32 px，H2 约 22–24 px，H3 约 18–20 px | 保留明显层级，同时控制长中文标题的换行和首屏占用；取消封面式标题处理 |
| 段落与列表 | 段落间距统一；同一列表内的间距更紧凑；保留层级缩进 | 让说明、步骤和嵌套结构易于扫读，避免每个条目独立成卡片 |
| 表格 | 字重明确的表头、轻分隔线或轻斑马纹；保留 Markdown 列对齐 | 提升比较效率；宽表局部滚动，不压缩到文字逐字换行 |
| 代码 | 等宽字体、适中字号与稳定行高；行内代码和代码块分开处理 | 保留空白和语法可读性；长代码局部滚动，语言标签有信息时才出现 |
| 引用 | 普通引用采用细左线与缩进，保持清楚的文字对比度 | 区别于正文；只有原文表达提示或警告语义时才使用相应提示块 |
| 明暗主题 | 宿主实际提供时优先使用宿主的背景、文字、边线和字体变量；否则使用中性回退 | 明暗均需检查弱化文字和高亮 token 的对比；减少装饰色与不必要的多层表面 |
| 窄分栏 | 先压缩外侧留白与标题间距，保留正文舒适字号 | 在 320、420、640 px 检查真实换行；正文不产生全页横向滚动 |
| 图片、公式与图表 | 尺寸自适应，复杂二维内容按需局部滚动 | 避免无条件再套一层视觉卡片；保留内容本来的背景和比例 |

表格、代码与引用的结构参考 Primer 和 VitePress 的正文实现；建议不直接复制它们的所有数值或装饰。[Primer 表格](https://github.com/primer/css/blob/main/src/markdown/tables.scss)、[Primer 代码](https://github.com/primer/css/blob/main/src/markdown/code.scss)、[Primer 正文及引用](https://github.com/primer/css/blob/main/src/markdown/markdown-body.scss)、[VitePress 正文](https://github.com/vuejs/vitepress/blob/main/src/client/theme-default/styles/components/vp-doc.css)

## 如何确认方向

先用同一份混合文档展示三条路线，内容包括长中文标题、段落、步骤、嵌套列表、表格、代码和引用。比较视图应同时包含宽窗、窄分栏、浅色和深色，避免仅用有漂亮封面和规整内容的示例判断。

先评价「是否像一份愿意长期阅读的 Markdown 文档」以及标题、表格、代码的阅读效率，再选定默认路线。自动检查负责发现溢出、遮挡、对比度和重排问题；用户评价负责确认审美方向。风格确定后再调整插件实现，并将源码验证与已安装插件的实际表现分别确认。

## 本轮独立对照与本地测量

已在本地生成独立研究对照页。对照页使用现有混合元素 fixture、真实 README 和兼容性说明，提供三条路线、明暗主题及 400、640、900 px 分栏。宿主文件标签栏只是位置示意，未连接当前 Codex 样式。候选稿使用中性回退配色，不代表已经消费了宿主样式变量。

在 400 px 分栏、浅色主题和相同文档内容下，候选稿测得：

| 指标 | 中性融合 | 清晰技术 | 舒展笔记 |
| --- | ---: | ---: | ---: |
| 正文字号 | 16 px | 16 px | 16 px |
| 正文有效宽度 | 364 px | 364 px | 364 px |
| H1 字号 | 28 px | 30 px | 29 px |
| README 首个 H2 距阅读区顶部 | 250 px | 260 px | 271 px |
| 兼容性说明首个 H2 距阅读区顶部 | 92 px | 105 px | 104 px |

上一轮出版风格在相同 400 px 分栏中，真实 README 首个 H2 距阅读区顶部约为 357 px。这个差异支持减少首屏装饰的判断，但不能证明用户必然偏好中性路线。正文开头有多少原始内容仍会影响首章位置，不能为达到固定指标而删减或改写文档。

54 组样本、路线、主题和宽度组合未发现全页横向溢出或未捕获浏览器错误；公式和流程图仍按现有渲染链路呈现。这是独立研究稿验证，不能代替 Codex 实际窗口和已安装插件验证。

研究阶段保留了上一轮未应用的草稿，未改动 `viewer.html`、`reader.js` 或测试。该草稿的一项工具栏回归断言期望没有 SVG 图标，而草稿新增了两个图标；后续 A 方向实施已移除这些图标。

## A 方向确认与实施

用户随后确认采用 A 中性融合文档，优先使用宿主字体和配色，缺失时默认。源码现已采用自然标题、普通引用、轻表格与主题一致的代码表面，移除封面、装饰包装和 SVG 工具图标。

桥接已保留 MCP Apps 宿主上下文并监听变更，宿主字体、配色和主题通过独立 appearance module 应用；不存在时使用本地中性回退，浅色背景为纯白 `#FFFFFF`，深色背景为 `#191919`。自定义字体只加载本地或内嵌字体来源，保持已有资源策略。真实 Codex 是否发送这些信息、已安装插件的实际效果与本地模拟测试仍需区分；当前改动未应用到安装缓存。
